# Streaming a source as RDF messages

This folder streams a time series source as RDF messages, following the RDF Message Stream Profile of the specification ([`spec/spec.bs`](../spec/spec.bs), section "RDF Message Stream Profile").

A source is a table: a description, and rows in a data file. An RDF Message Log is a stream of small RDF documents. `make_messages.py` turns one into the other.

## Files

| File | What it is |
| --- | --- |
| `zevenaarshaven_ec20.csv` | The data file: five readings of the electrical conductivity at 20 °C (EC20) of the water at Kanaal Gent-Terneuzen Zevenaarshaven (NL), with the quality code colour of each reading. These are the five readings of `../metadata endpoint/waterinfo_289441042_tss2_points_embedded.ttl` (Waterinfo). |
| `zevenaarshaven_ec20.ttl` | The metadata document: an immutable `tss:CSVSource` with three fields and the stored summaries. The time field and the quality colour are context fields (`tss:ContextField`); the EC20 field is a value field (`tss:ValueField`). The quality colour describes the EC20 readings, with its own property `ex:qualityCodeColor`. |
| `zevenaarshaven_ec20_messages.ttl` | The same rows as an RDF Message Log (`VERSION "1.2-messages"`), generated by `make_messages.py`. |
| `make_messages.py` | Reads the metadata document and its data file, and writes the log. |

## A source of its own

The metadata document of a CSV source links to no points: its rows are in its data file. The specification only lets the expansion of a source link it to points, and the expansion is not a metadata document. So the log describes a `tss:EmbeddedRDFSource` of its own, `:source`, with the same rows, and its merge stays a metadata document that the demo 11 SHACL shapes accept:

- `:source prov:wasDerivedFrom ex:zevenaarshaven-csv-source` links it to the CSV source it was read from.
- Its IRIs are in the log itself, with the prefix `PREFIX : <#>`: `:source`, and the fields `:time-field`, `:ec20-field` and `:quality_color-field`, named after their columns.
- It keeps the labels, the window, the key, and the kinds, datatypes and meaning of the fields. It leaves out what describes the data file: `tss:dataFile` and, for other sources, `tss:delimiter`, `tss:encoding`, `tss:header`, a time grid, a value encoding or `tss:aboutUrl`.
- The quality colour keeps its property, `ex:qualityCodeColor`, so its values have the same predicate as in the expansion of the CSV source.

## The messages

The log holds 7 messages, each ended by the delimiter `MESSAGE`:

| # | Kind | What it holds | Focus nodes | Timestamp |
| --- | --- | --- | --- | --- |
| 1 | description | `<> dcterms:conformsTo tss:MessageStreamProfile`, `:source` and its three fields, without `tss:immutable` and the summaries | `:source` | none |
| 2–6 | row | one row of the CSV file: `:source tss:hasPoint` one point for each value field with a value; here one, the EC20 reading | the points | `tss:time` on its points |
| 7 | ending | `:source tss:immutable true`, and the stored summaries of the CSV source, which describe the same readings | `:source` | none |

A row message, for the first CSV line `2021-03-03T23:15:00Z,4797.72,"rgba(0, 128, 0, 1.0)"`:

```turtle
:source tss:hasPoint [
    tss:field :ec20-field ;
    tss:time "2021-03-03T23:15:00Z"^^xsd:dateTime ;
    tss:value "4797.72"^^xsd:double ;
    ex:qualityCodeColor "rgba(0, 128, 0, 1.0)"^^xsd:string
] .
MESSAGE
```

The source has one value field, so a point could leave out `tss:field`. The log states it anyway, so that a consumer that starts reading after message 1 still knows which field each reading belongs to.

An RDF stream processing engine reads it like this:

1. From message 1, it learns that `:ec20-field` is the electrical conductivity in µS/cm, that `:quality_color-field` describes it (`tss:describesField`) with `ex:qualityCodeColor`, and where the rows come from (`prov:wasDerivedFrom`). It keeps this.
2. From each row message, it takes the points as the focus nodes, and `tss:time` as the timestamp; it does not need message 1 for that. It can then, for example, average the EC20 readings per hour.
3. From message 7, it learns that nothing more will come, and gets the stored summaries.

## Run it

```bash
python make_messages.py zevenaarshaven_ec20.ttl
```

It needs `rdflib`. It writes `zevenaarshaven_ec20_messages.ttl` next to the metadata document; `--output` writes it elsewhere. It only supports CSV sources without a time grid and without a value encoding. Literals keep the text they have in the metadata document and the data file.

## Compared with the specification upstream

The [upstream specification](https://github.com/KNowledgeOnWebScale/rdf-tss) writes the expansion of a CSV, Parquet or Arrow source as messages directly: its RDF Message Stream Profile example states `ex:csv-source tss:hasPoint [...]` on the `tss:CSVSource` itself. The merge of such a stream is not a metadata document that meets the specification, since an external source has no `tss:hasPoint`. Demo 11 streams such a source as a `tss:EmbeddedRDFSource` of its own instead, derived from it with `prov:wasDerivedFrom`.
