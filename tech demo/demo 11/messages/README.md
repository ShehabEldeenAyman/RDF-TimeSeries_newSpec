# Streaming a source as RDF messages

This folder streams a time series source as RDF messages, following the RDF Message Stream Profile of the specification ([`spec/spec.bs`](../spec/spec.bs), section "RDF Message Stream Profile").

A source is a table: a description, and rows in a data file. An RDF Message Log is a stream of small RDF documents. `make_messages.py` turns one into the other.

## Files

| File | What it is |
| --- | --- |
| `zevenaarshaven_ec20.csv` | The data file: five readings of the electrical conductivity at 20 °C (EC20) of the water at Kanaal Gent-Terneuzen Zevenaarshaven (NL), with the quality code colour of each reading. These are the five readings of `../metadata endpoint/waterinfo_289441042_tss2_points_embedded.ttl` (Waterinfo). |
| `zevenaarshaven_ec20.ttl` | The metadata document: an immutable `tss:CSVSource` with three fields (time, EC20, quality colour) and the stored summaries. |
| `zevenaarshaven_ec20_messages.ttl` | The same readings as an RDF Message Log (`VERSION "1.2-messages"`), generated by `make_messages.py`. |
| `make_messages.py` | Reads the metadata document and its data file, and writes the log. |

## A source of its own

Only a `tss:EmbeddedRDFSource` links to points with `tss:hasPoint`: in the vocabulary, its domain is `tss:EmbeddedRDFSource`. Linking the CSV source to points would make it a CSV source and an embedded source at once, which the specification does not allow. So the log describes a `tss:EmbeddedRDFSource` of its own, `:source`, with the same readings:

- `:source prov:wasDerivedFrom ex:zevenaarshaven-csv-source` links it to the CSV source it was read from.
- Its IRIs are in the log itself, with the prefix `PREFIX : <#>`: `:source`, and the fields `:time`, `:ec20` and `:quality_color`, named after their columns.
- It keeps the labels, the window, the key, and the datatypes and meaning of the fields. It leaves out what describes the data file: `tss:dataFile` and, for other sources, `tss:delimiter`, `tss:encoding`, `tss:header`, a time grid or a value encoding.

The merge of the messages is so the metadata document of an immutable `tss:EmbeddedRDFSource`, which the demo 11 SHACL shapes accept.

## The messages

The log holds 7 messages, each ended by the delimiter `MESSAGE`:

| # | Kind | What it holds | Focus node | Timestamp |
| --- | --- | --- | --- | --- |
| 1 | description | `<> dcterms:conformsTo tss:MessageStreamProfile`, `:source` and its three fields, without `tss:immutable` and the summaries | `:source` | none |
| 2–6 | point | one row of the CSV file: `:source tss:hasPoint` one point, with the IRI of each field as predicate | the point | the point's value for `:time` |
| 7 | ending | `:source tss:immutable true`, and the stored summaries of the CSV source, which describe the same readings | `:source` | none |

A point message, for the first CSV line `2021-03-03T23:15:00Z,4797.72,"rgba(0, 128, 0, 1.0)"`:

```turtle
:source tss:hasPoint [
    :time "2021-03-03T23:15:00Z"^^xsd:dateTime ;
    :ec20 "4797.72"^^xsd:double ;
    :quality_color "rgba(0, 128, 0, 1.0)"^^xsd:string
] .
MESSAGE
```

An RDF stream processing engine reads it like this:

1. From message 1, it learns that `:time` is the time field (`tss:timeField`), that `:ec20` is the electrical conductivity in µS/cm, that `:quality_color` describes the EC20 value (`tss:describesField`), and where the readings come from (`prov:wasDerivedFrom`). It keeps this.
2. From each point message, it takes the point as the focus node, and the value of the time field as the timestamp. It can then, for example, average the EC20 values per hour.
3. From message 7, it learns that nothing more will come, and gets the stored summaries.

## Run it

```bash
python make_messages.py zevenaarshaven_ec20.ttl
```

It needs `rdflib`. It writes `zevenaarshaven_ec20_messages.ttl` next to the metadata document; `--output` writes it elsewhere. It only supports CSV sources without a time grid and without a value encoding. Literals keep the text they have in the metadata document and the data file.

## Compared with PR #33

[PR #33](https://github.com/KNowledgeOnWebScale/rdf-tss/pull/33) builds on PR #31, which demo 11 does not have yet. There, a row message holds one point per value field, each linked to its field with `tss:field`, with its time stated with `tss:time` and its value with the field's `tss:property`. An engine then finds the timestamp without the description message. In demo 11, a point is a row, the IRI of each field is the predicate of its values, and an engine reads the description message to find the time field.

PR #33 also links the original source to the points: in the playground, a `tss:ParquetSource` states `tss:hasPoint`, which the specification does not allow for an external source. Demo 11 streams such a source as a `tss:EmbeddedRDFSource` of its own instead, derived from it.
